# ประสิทธิภาพ

ตัวเลขทั้งหมดวัดจริงบนระบบที่ deploy แล้ว: GPU node = RTX PRO 4000 Blackwell
(sm_120), voice host = OrbStack VM `aarch64` ไม่มี GPU, เชื่อมกันผ่าน Tailscale

## แยกตามขั้นตอน

| ขั้นตอน | เวลา | หมายเหตุ |
|---|---|---|
| เครือข่าย host → GPU node | ~20 ms | Tailscale RTT |
| **STT** (`large-v3` float16) | **0.50 s** | คลิป 3 วินาที → RTF **8.3×** |
| **LLM ดิบ** (ยิงตรงไป gateway) | **0.93 s** | `gemma4-26b`, ttfb |
| **Hermes agent เต็มเทิร์น** | **~5–7 s** | ส่วนที่เหลือคือ overhead ของ agent |
| **TTS** (F5-TTS-TH v2) | **0.59–1.02 s** | เร็วกว่า realtime 3.4–7× |
| **รวม พูด → ได้ยินเสียงตอบ** | **6–9 s** | |

## คอขวดอยู่ที่ agent ไม่ใช่ระบบเสียง

นี่คือข้อสรุปที่สำคัญที่สุดของหน้านี้ · เอา 0.50 (STT) + 0.93 (LLM) + 0.59
(TTS) = **~2 วินาที** แต่ของจริงคือ 6–9 วินาที ส่วนต่าง **~5 วินาที** เกิดขึ้น
ระหว่างที่ Hermes ประกอบเทิร์น — system prompt ที่รวม skill กว่า 80 ตัว,
การดึง memory, การประกอบ tool schema, session handling

**การจูนโมเดลเสียงจะไม่ช่วย** ลด `step` ของ TTS จาก 32 เหลือ 24 ประหยัดได้
~0.2 วินาทีจากทั้งหมด 7 วินาที · ที่คุ้มกว่าคือลดภาระของ agent:

| วิธี | ผลที่คาด | ผลข้างเคียง |
|---|---|---|
| จำกัด toolset ของ session เสียง | มาก — prompt สั้นลงชัดเจน | agent ทำอะไรได้น้อยลงตอนคุยด้วยเสียง |
| `agent.reasoning_effort: low` | ปานกลาง | คำตอบคิดน้อยลง กระทบทุกการใช้งานของ Hermes ไม่ใช่แค่เสียง |
| สั่งให้ตอบสั้นใน `hermes.instructions` | ปานกลาง | ทำอยู่แล้ว — คำตอบสั้นสังเคราะห์เร็วกว่า |
| ใช้โมเดลเล็กลงสำหรับ session เสียง | มาก | คุณภาพคำตอบลด |

> ทั้งหมดนี้เป็นการตัดสินใจเรื่องพฤติกรรมของ agent ซึ่งกระทบการใช้งานอื่น
> ด้วย จึงไม่ได้ตั้งค่าไว้ให้ล่วงหน้า

## เทิร์นแรกของ process ที่เย็น — 30 วินาที

วัดจาก turn log ของ server เอง:

| เทิร์น | `llm_time_to_first_token` |
|---|---|
| 1 | **29.9 s** |
| 2 | 0.64 s |

คำถามที่สองไม่ได้ง่ายกว่า · สิ่งที่ต่างคือ system prompt กับ tool schema ~90 KB
ที่อยู่ข้างหน้ามัน**ผ่านโมเดลไปแล้วหนึ่งรอบ** · นี่คือ prefill ไม่ใช่การคิด และ
ผู้ใช้จ่ายมันด้วยการพูดใส่ไมค์แล้วรอครึ่งนาที

`host/patches/apply_voicemode.py` จ่ายมันตอนที่ไม่มีใครรอ — ตอน start, ตอน
client ต่อเข้ามา, และ heartbeat ทุก 60 วินาทีระหว่างที่ยังมีคนต่ออยู่ (ไม่วอร์ม
ตอนไม่มีใคร — process ที่วอร์มทั้งคืนคือค่าใช้จ่าย ไม่ใช่ฟีเจอร์)

วอร์มบน session ทิ้ง **โดยตั้งใจ**: prefix cache คิดจากเนื้อหา ดังนั้น session
อื่นที่มี system prompt เดียวกันก็วอร์มส่วนที่แพงให้ และบทสนทนาจริงของผู้ใช้
ต้องไม่มีเทิร์นวอร์มปนอยู่

ตรวจ: `curl -H "X-Jarvis-Token: $JARVIS_HUD_TOKEN" https://<host>:8766/api/warm`

## วัดทั้งระบบ — 55 เทิร์นจริง

ไม่ใช่ค่าเฉลี่ยจากเทิร์นเดียว แต่เป็นการกระจายของ 55 เทิร์นที่มีเสียงพูดจริง:

| ชั้น | กลาง | p90 | สูงสุด |
|---|---|---|---|
| STT ถอดเสียง | 0.46s | 0.87s | 1.90s |
| **LLM โทเคนแรก** | **2.28s** | **19.93s** | **56.74s** |
| TTS ไบต์เสียงแรก | 1.26s | 2.11s | 3.39s |
| **จบประโยค → เสียงแรก** | **6.08s** | 18.33s | 63.01s |

แยก LLM ออกตามว่าเรียกเครื่องมือหรือไม่ แล้วภาพเปลี่ยนทันที:

| | n | กลาง | p90 |
|---|---|---|---|
| ไม่เรียกเครื่องมือ | 34 | **1.30s** | 16.02s |
| เรียกเครื่องมือ | 16 | **6.05s** | 14.13s |

และเทิร์นที่ช้าที่สุดโดยไม่เรียกเครื่องมือเลย ล้วนเป็นประโยคเดียวกัน —
*"สวัสดีครับ ระบบพร้อมทำงานไหม"* ที่ 29–35 วินาที · **นั่นคือเทิร์นแรกหลัง restart**
ซึ่งวันนั้นผม restart ไปสิบกว่ารอบเพื่อ deploy

### สิ่งที่แก้แล้ว — ก้อนเสียงแรกต้องสั้น

F5-TTS สังเคราะห์ทั้งก้อนให้เสร็จก่อนคืนอะไรออกมา **ก้อนแรกจึงคือเวลารอทั้งหมด**
วัดบน node จริง:

| ความยาว | เวลา |
|---|---|
| 12 ตัวอักษร | 0.56s |
| 61 ตัวอักษร | 0.70s |
| 138 ตัวอักษร | 1.21s |
| 408 ตัวอักษร | 1.55s |

คงที่ราว 0.5 วินาที บวกอีก 2.5 มิลลิวินาทีต่อตัวอักษร

**ภาษาไทยมักไม่มีเครื่องหมายจบประโยคเลย** คำตอบทั้งอันจึงมาเป็นก้อนเดียว
และห้องก็รอ 1.2 วินาทีกว่าจะได้ยินเสียงแรก

ตอนนี้**ก้อนแรกถูกตัดสั้นที่ช่องว่าง** (ซึ่งในภาษาไทยคือรอยแบ่งวรรค ไม่ใช่รอยแบ่งคำ)
วัดได้ **1.26s → 0.65s** · ก้อนที่เหลือสังเคราะห์ระหว่างที่ก้อนแรกกำลังเล่นอยู่
จึงไม่เสียอะไรเลย · รอยต่อที่เราตัดเองใช้ช่องว่าง 40 มิลลิวินาที ไม่ใช่ 140
เพราะมันไม่ใช่จุดจบประโยค

### สิ่งที่ยังเหลือ — เรียงตามผลกระทบ

| ประเด็น | ราคา | ทำอะไรได้ |
|---|---|---|
| เทิร์นแรกหลัง restart | +28s | warm-up ครอบ prefix ร่วมได้ แต่ไม่ครอบประวัติของเซสชันเอง |
| เรียกเครื่องมือ 1 ครั้ง | +4.7s | ทุกครั้งคือ prefill ใหม่ทับ prompt ทั้งอัน — **ลด toolset = ถูกลงทุกเทิร์น** (ตอนนี้เปิด 16 ชุดบน `cli`) |
| VAD รอความเงียบ | 650ms | ลดได้ แต่ผิดพลาดแล้วตัดคำพูดคนกลางประโยค — ปรับเองได้ที่ `localStorage.jarvisVad` |
| STT beam 5 | ~0.2s | ลดเป็น 1 ได้ แต่แลกความแม่น |

**ตัวที่คุ้มที่สุดที่เหลือคือ toolset** — เครื่องมือ 16 ชุดอยู่ใน prompt ทุกเทิร์น
ไม่ว่าจะใช้หรือไม่ และทุกการเรียกเครื่องมือต้อง prefill ทับมันอีกรอบ

## เซสชันที่โตไม่หยุด — สาเหตุที่ทำให้ "เหมือน agent ไม่ตอบ"

อาการที่ผู้ใช้รายงาน: กดคุยต่อเนื่อง พูดไป **agent ไม่ตอบ** ต้องกดออกจากโหมด
ถึงจะได้คำตอบ

แต่ turn log บอกอีกอย่าง:

```
interrupted: 0          ← ไม่มีเทิร์นไหนถูกยกเลิก
ทุกเทิร์นมี ttfa        ← มีเสียงออกทุกเทิร์น
```

**มันตอบทุกครั้ง** — แค่ช้าจนคนคิดว่ามันไม่ตอบ:

| | end of speech → เสียงแรก |
|---|---|
| ตอนวัดครั้งแรก | **1.9 วินาที** |
| ตอนนี้ | **3 – 27 วินาที** |

สาเหตุอยู่ที่เซสชัน:

```
message_count : 395        ← สะสมมาสองวัน
input_tokens  : 9,233,574  ← สะสม ≈ 46,000 โทเคน/เทิร์น
```

เซสชันเสียงเป็นแบบถาวรโดยออกแบบ (เพื่อให้คุยต่อเนื่องได้) แต่มัน**ไม่เคยถูกตัด** ·
ทุกเทิร์นจึงจ่าย prefill ทับประวัติทั้งหมด และเมื่อชนเกณฑ์ compression ของ Hermes
(`threshold: 0.5` = ครึ่งหนึ่งของ 131k) จะมีเทิร์นหนึ่งที่ช้าเป็นพิเศษ — นั่นคือ
เทิร์น 27 วินาที

**สิ่งที่ทำ:**

1. **หมุนเซสชันทุก 40 เทิร์น** (`JARVIS_SESSION_MAX_TURNS`) · บทสนทนาด้วยเสียง
   ต้องการแค่ไม่กี่นาทีล่าสุด ไม่ใช่สองวันล่าสุด · **ความจำระยะยาวต้องอยู่ใน vault**
   ซึ่งค้นได้และไม่ต้องจ่าย prefill ทุกครั้ง
2. **นับเวลารอให้เห็น** — เกิน 4 วินาทีจะขึ้นตัวเลขวินาทีทั้งบนแถบสถานะและในข้อความ ·
   เงียบ 20 วินาทีโดยไม่มีอะไรบอก คือสิ่งที่ทำให้คนเอื้อมไปกดปุ่ม

## คำรับทราบ — ตอนนี้รอก่อน

`ACK_TEXTS` (`ครับ`, `ได้ครับ`, `รับทราบครับ`) เคยเล่น**ทันที**ที่ส่งเทิร์น
ซึ่งถูกตอนที่เทิร์นใช้เวลา 6–14 วินาที · แต่มันเล่น**ก่อนที่ใครจะรู้ว่ามีเทิร์น
จริงไหม** — เสียงรบกวนที่หลุด VAD เข้ามาถูกตอบรับออกเสียง แล้วเซิร์ฟเวอร์ค่อยทิ้ง
เพราะไม่มี transcript · ผลคือ agent พูด "ครับ" กับห้องว่าง

ตอนนี้ end-of-speech → เสียงแรกวัดได้ **1.9 วินาที** จึงเปลี่ยนเป็น *arm* แทน
*play*: ตั้งเวลา `VAD.ackDelayMs` (1800 ms) แล้วยกเลิกเมื่อ

- ไบต์แรกของคำตอบจริงมาถึง (`playChunk`)
- หรือกลับไป standby โดยไม่ได้พูดอะไรเลย (เทิร์นถูกทิ้ง)

เทิร์นปกติจึงตอบตัวเองก่อนเสมอ และคำรับทราบจะดังเฉพาะเทิร์นที่ค้างจริง ๆ

> **"อืม" ถูกถอดออก** — มันเป็นเสียงลังเล ไม่ใช่เสียงรับรู้ · ออกมาจากเครื่องแล้ว
> ฟังเหมือนเครื่องไม่แน่ใจ ซึ่งตรงข้ามกับหน้าที่ของคลิปนี้พอดี ·
> `/api/ack?i=` ตอบ 404 เมื่อเกินจำนวนที่มี HUD จึงดึงจนกว่าจะหมด
> ไม่ต้องรู้ล่วงหน้าว่ามีกี่คลิป

## เส้นทางไปยัง LLM สำคัญกว่าที่คิด

วัดจากเครื่องจริง ยิงคำขอเดียวกันไปยัง gateway ตัวเดียวกัน ต่างกันแค่เส้นทาง:

| เส้นทาง | prompt สั้น | prompt ยาว (67 KB) ครั้งแรก | ครั้งที่สอง |
|---|---|---|---|
| ผ่านโดเมนสาธารณะ (https + CDN) | 0.57s | 1.33s | 0.45s |
| ตรงเข้า gateway (http, พอร์ต forward) | **0.16s** | **0.19s** | **0.17s** |

ส่วนต่างส่วนใหญ่คือ TLS handshake กับ hop ของ CDN — `connect` อย่างเดียวต่างกัน
0.22s vs 0.03s · และเส้นทางตรงไม่ต้องพึ่ง cache เลย เพราะ prefill เร็วอยู่แล้ว

**แต่มันไม่โผล่ในเวลาต่อเทิร์นอย่างที่ควรจะเป็น** — เทิร์นจริงยังอยู่ที่ 6–14
วินาทีทั้งก่อนและหลัง เพราะความแกว่งจาก Hermes เองและความยาวคำตอบที่ไม่เท่ากัน
กลบส่วนต่างระดับ 0.4 วินาทีจนหมด

บทเรียน: **วัดทีละชั้นก่อนสรุป** การเร่งชั้นที่ไม่ใช่คอขวดให้เร็วขึ้น 3 เท่า
อาจไม่เปลี่ยนอะไรที่ผู้ใช้รู้สึกเลย

### สิ่งที่ลองแล้วไม่ได้ผล

ตัด toolset ของ session เสียงจาก 91 KB เหลือ 50 KB (tool schema 62 KB คือ
ส่วนที่ใหญ่ที่สุดของ prompt) · วัด 5 เทิร์นได้ 6.1 / 7.2 / 6.9 / 10.0 / 6.1
วินาที — **ไม่ต่างจากเดิม** จึงคืนค่ากลับ ไม่ควรลดความสามารถของ agent โดย
ไม่ได้ความเร็วกลับมา
